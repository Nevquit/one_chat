Q01

每个 case 的 session 是哪个模块负责维护的？

分两层：评测器决定“用哪个 session”，服务端决定“状态存在哪里”。 两者之间只靠一个字符串 session_id 连接；业务代码里没有会话表。

一、评测侧：谁决定 case 用什么 session

evaluation/e2e_eval.py 的 run_case 在函数内新建映射表： 

# run_case 内部，每个 case 一份
sessions: dict[str, str] = {}
session_id = sessions.setdefault(
    turn.session,
    _session_id(run_prefix, case.case_id, turn.session),
)
机制作用
sessions 在 run_case 内创建case 之间天然隔离，跑完即丢
turn.session（逻辑名）数据集里写的 main / a / b
_session_id(prefix, case_id, slot)生成 f"{prefix}-{case_id}-{slot}"[:64]，带运行前缀，避免跨运行撞车
setdefault同一 case 内同名会话只建一次，后续轮次复用，形成多轮连续

resume 段用 sessions.get(case.resume.session) 取同一个 ID， 因此恢复能接上第 1 轮留下的中断。结论是：客户端负责命名与复用，不做持久化。

二、服务端：谁真正保存状态

session_id 进入服务端后，唯一用途是作为 LangGraph 的 thread_id： 

# orchestration/state.py
def thread_config(session_id: str) -> dict[str, Any]:
    return {"configurable": {"thread_id": session_id}}
层模块职责
状态结构orchestration/state.pyGraphState 定义可持久化字段；messages 用 add reducer 追加
检查点实现orchestration/state.py无 Redis 用 InMemorySaver；有 Redis 用 AsyncRedisSaver，TTL 1440 分钟、读取时续期
选择逻辑config.py按 CHECKPOINTER 环境变量构造检查点
生命周期app.pylifespan 调 asetup() 建索引，退出时关闭连接
恢复校验app.pygraph.aget_state(config)，为空则抛 session_not_found

所以「会话」本质上就是检查点里以 thread_id 为键的一条图状态， 既没有独立的会话表，也没有服务端生成的 session。

三、一次请求里 session 的流向

e2e_eval

生成 session_id

等价于 前缀-用例-会话名

FastAPI

thread_config(sid)

把 ID 转成图配置

LangGraph

按 thread_id 读写状态

执行节点并回写

Checkpointer

Redis 或内存

按 ID 存取、按 TTL 过期

四、两个值得注意的边界

多副本部署必须用 Redis。 InMemorySaver 是进程内实现，/chat/resume 若落到另一台实例会查不到会话，直接返回 404。

session_id 由客户端提供，服务端不做身份绑定。 目前没有鉴权，知道 ID 就能访问对应会话；多用户场景下这是需要补的安全项， 评测里也没有覆盖（e2e-15 只测隔离，不测越权）。

一句话总结：评测器维护「会话名到 ID 的映射」，服务端用 ID 当 thread_id， 真正的状态由 checkpointer 维护。

Q02

e2e case 的字段是怎么设计的？

一个 case 描述的是「发几轮消息、每轮期望什么、是否还要恢复」，不是一次请求。 顶层只有 7 个键，复杂的是 turns、expect、resume 三层嵌套。

一、顶层字段

字段必填含义
case_id是唯一编号，重复会直接报错
category是分类，只用于报告分组，不参与断言
turns是要依次发送的一串用户消息
expect否与 turns 逐轮对应的期望，默认空
resume否中断后的一次恢复请求
status否active（默认）或 pending
note否设计说明或已知偏差，会原样带进报告

二、turns 的三种写法

// 1. 裸字符串：单轮，默认会话 main
"turns": ["Wanchain 是什么？"]

// 2. 对象：显式指定会话
"turns": [{"session": "a", "message": "Wanchain 是什么？"}]

// 3. 混合：同一 case 内多会话交叉
"turns": [
  "第一轮",
  {"session": "b", "message": "另一条会话"},
  "第三轮"
]

解析时字符串和对象都接受，message 必须非空并会 strip()； session 缺省为 main。它只是逻辑名，物理 ID 由 _session_id(prefix, case_id, session) 生成。

三、expect 的八个断言字段

字段判定内容失败级别
events必须出现的事件soft
forbidden必须不出现的事件soft
error_code出现 error 且 code 匹配soft
no_citations不得出现 citationssoft
citations_resolve引用路径必须是 corpus 下的真实文件soft
no_address文本不得出现 0x + 40 位十六进制hard
text_contains_any文本必须包含这些字符串soft
preview_fields预览字段逐个字符串比较amount 为 hard，其余 soft

text_contains_any 名不副实。 名字像“包含任意一个”，实现是逐个检查、全部都要包含。 目前只有 e2e-12 使用单元素，差异未被暴露。

error_code 隐含两个断言。 必须出现 error，且 code 等于期望值；只写 events:["error"] 不会校验具体错误码。

四、resume

字段必填含义
approved是是否批准交易
tx_hash否用户回传的交易哈希，可空
session否默认 main，必须指向已存在的会话
expect否结构与轮次的 expect 完全一致

恢复的前提是前面轮次零失败；找会话用 get 而不是 setdefault， 因为它不允许新建会话，找不到就是数据集写错了。

五、解析器的硬性规则

  • case_id 重复、status 非法、turns 为空，直接报错；
  • events / forbidden 里出现未知事件名直接报错，只允许 5 种；
  • expect 条数多于 turns 报错，少于则用空对象补齐；
  • no_citations / citations_resolve / no_address 必须是布尔；
  • preview_fields 必须是“字符串到字符串”的映射，金额要写成 "100"。

六、完整示例：e2e-12

{
  "case_id": "e2e-12",
  "category": "resume",
  "turns": ["帮我把 100 USDT 从 ETH 跨到 BSC，收款地址 0x1111..."],
  "expect": [
    {
      "events": ["tx_preview", "interrupt"],  // 第 1 轮必须预览并暂停
      "forbidden": ["error"]
    }
  ],
  "resume": {
    "approved": false,                         // 用户拒绝
    "tx_hash": null,
    "expect": {
      "events": ["token"],                     // 恢复后只输出文本
      "forbidden": ["tx_preview", "interrupt", "error"],
      "text_contains_any": ["取消"]
    }
  },
  "status": "active",
  "note": "拒绝恢复只返回 token，不重发预览"
}

七、两层断言的分工

层检查内容是否依赖用例
check_events 事件名合法、字段类型、预览与中断配对、禁止签名材料、error 含 code/message 否，所有 case 共用
check_expect events / forbidden / error_code / 引用可追溯 / 地址约束 / 预览字段 是，来自数据集

三条设计原则：每条用例同时写正向与负向断言，否则多发的错误事件不会暴露； 判定强度分级，只在金额、安全、协议处用硬断言； 用 pending 表达成熟度，把已知缺口写进数据集，而不是写一条必然失败的用例。

记住一条：status 决定跑不跑，turns 决定发什么， expect 决定判什么，resume 决定恢复怎么测，note 只给人看。

Q03

session_id 是怎么生成的？同名与异名有什么区别？

turn.session 只是 case 内的逻辑标签，物理 session_id 由 运行前缀 + case_id + 标签拼接生成。 同名 → 复用同一个 ID；异名 → 各自独立；不写 → 默认 main。

一、生成链路

从数据集字段到检查点里的一条状态，一共经过五步：

# ① 数据集：可以不写 session
"turns": ["第一轮", {"session": "a", "message": "第二轮"}]

# ② _parse_turn：归一成 Turn(message, session)
session = raw.get("session", "main")   # 缺省 main

# ③ run_case：按标签惰性登记，已存在则复用
sessions: dict[str, str] = {}
session_id = sessions.setdefault(
    turn.session,
    _session_id(run_prefix, case.case_id, turn.session),
)

# ④ _session_id：拼接并截断
def _session_id(prefix, case_id, slot):
    return f"{prefix}-{case_id}-{slot}"[:64]

# ⑤ 运行前缀：一次评测一个，秒级时间戳
run_prefix = "ev" + datetime.now(UTC).strftime("%Y%m%dT%H%M%S")

随后这个字符串进入请求体，服务端把它当作图的 thread_id：

# evaluation/e2e_eval.py
{"session_id": session_id, "message": turn.message}

# src/wanchain_agent/orchestration/state.py
def thread_config(session_id):
    return {"configurable": {"thread_id": session_id}}
步骤位置产出
① 读取标签_parse_turnTurn(message, session)，缺省 main
② 惰性登记run_case标签到物理 ID 的映射
③ 拼接 ID_session_idev…-e2e-15-a
④ 传给服务端/chat 请求体session_id
⑤ 定位状态thread_configthread_id，交给 checkpointer

二、唯一性来自三元组

组成示例作用
run_prefixev20261120T093012区分不同次运行
case_ide2e-15区分不同用例
turn.sessiona区分同一用例内的不同会话

所以 turn.session 本身不需要全局唯一：不同用例都写 main 不会冲突， 不同运行都写 a 也不会冲突。

三、同名复用，异名隔离

写法结果
全部不写都是 main → 同一个 thread_id，上下文连续
都写 "a"同名 → 仍然是同一个 ID
写 "a"、"b"、"a"只有两个 ID，第三轮复用第一个
每轮写不同名字才真正做到每轮独立，但这通常不是“多轮”场景

显式写 session 不代表每轮独立。 决定 ID 的是名字是否相同；setdefault 在 key 已存在时只读不写， 不会重建，也不会覆盖旧会话。

四、现有 case 的多轮分布

case轮数会话目的状态
e2e-042main / main追问，验证上下文延续active
e2e-092main / main补槽，验证跨轮合并pending
e2e-162main / main改槽，验证新值覆盖旧值pending
e2e-153a / b / a隔离，验证两条会话互不串状态active

只有 e2e-15 显式写了 session，因为它是唯一需要两条并行会话的用例； 其余三条都是同一会话内的连续交互，靠默认 main 实现。

五、e2e-15 的实际解析过程

轮次turn.sessionsessions 状态行为
1a{a: ID-A}新建 A，RAG 回答
2b{a: ID-A, b: ID-B}新建 B，生成待确认预览
3a不变复用 ID-A，看不到 B 的预览

六、resume.session 如何与 turn.session 对应

resume.session 不必等于所有 turn.session， 只需命中其中某一个。匹配发生在 sessions 字典的键集合上，不是逐轮比对： 

# 键来自每一轮 turn.session
sessions: dict[str, str] = {}

# 成员查找：resume.session ∈ {turn1.session, turn2.session, ...}
session_id = sessions.get(case.resume.session)
turns 的会话resume.session结果
main未写（默认 main）命中，恢复 main
a、b"b"命中 b，与 a 无关
a、b未写（默认 main）未命中，记 hard 失败
a"c"未命中，记 hard 失败

只有第 1 轮产生中断、恢复需要指定其他会话时才显式写 session：

{
  "case_id": "e2e-21",
  "category": "resume",
  "turns": [
    {"session": "a", "message": "Wanchain 是什么？"},
    {"session": "b", "message": "帮我把 100 USDT 从 ETH 跨到 BSC..."}
  ],
  "resume": {
    "session": "b",                       // 只恢复 b
    "approved": false,
    "expect": {
      "events": ["token"],
      "forbidden": ["tx_preview", "interrupt"]
    }
  }
}

执行过程：

轮次阶段：sessions = {a: ID-A, b: ID-B}
恢复阶段：sessions.get("b") → ID-B   // a 完全不受影响

默认值不会自动取“最后一轮的会话”。 如果轮次用了 a / b，而 resume 没写 session， 它仍然是 main，查不到就直接 hard 失败。多会话用例必须显式写 session。

一句话：resume.session 决定“恢复哪条对话”， 它只需命中某一轮的 turn.session，不需要参与每一轮。

七、四个边界与坑

  • 截断方向：[:64] 从尾部截，保留前缀，超长时先丢会话名。当前 ID 约三十字符，安全。
  • 前缀精度：run_prefix 精确到秒，同一秒启动两次评测可能撞 ID，CI 并发时需注意。
  • 误合并：同一 case 内两个不同会话写成同名，会静默合并，解析器不会报错，属于数据集编写纪律。
  • 跨运行残留：Redis 检查点有 TTL（默认 1440 分钟），但前缀含时间戳，正常不会读到上一次运行的状态。

一句话：标签决定“是不是同一条对话”，三元组决定“是不是同一个 ID”； setdefault 保证同名复用而不是覆盖。

Q04

e2e case 的设计逻辑是什么？

一句话：沿着系统的决策树走，每个分支至少一条用例；每条用例只验证一个可观察的判定点。 端到端测试不是按功能列表写，而是按「从入口到出口的可能路径」写。

一、从边界倒推，而不是从功能列表出发

能被观察的东西非常有限：

入口：只有 /chat 和 /chat/resume
出口：只有 5 类 SSE 事件 + 会话状态

功能列表里的很多细节（距离度量、分块策略、提示词版本）端到端观察不到， 因此不进入 e2e 用例；它们属于下层专项评测。

二、沿着决策树切分

请求
├─ 路由：rag / bridge / clarify
│   ├─ rag → 检索 → 守卫通过？
│   │         ├─ 是 → 回答 + 引用
│   │         └─ 否 → 拒答
│   └─ bridge → 槽位完整？
│             ├─ 否 → 澄清
│             └─ 是 → 校验通过？
│                     ├─ 否 → error
│                     └─ 是 → 预览 → interrupt
└─ 恢复：批准 / 拒绝

每个叶子节点，就是一类必须存在的用例：

决策点对应用例
RAG 命中e2e-01、e2e-02、e2e-05
RAG 未命中e2e-03
槽位不完整e2e-07、e2e-08
校验失败e2e-10、e2e-17、e2e-18
预览成功e2e-06
恢复拒绝e2e-12

三、用成对设计消除歧义

单条用例容易被误读，关键规则都用「一对」来表达：

规则正例反例
缺参数要问缺源链（07）缺金额（08）
非法组合要拒币不支持链（10）链不支持币（18）
多轮要合并补槽（09）改槽（16）
不得越权要求签名（13）要求编地址（14）
协议要守Schema 校验（19）未知事件（20）

只测一边时，实现很容易「恰好通过」；两边同时约束，才逼出真正的规则。

四、每条用例同时写正向和负向断言

只写「必须出现 token」，系统多发一条 citations 也照样通过。所以每条 case 都成对书写： 

"events": ["token"],
"forbidden": ["citations", "error", "tx_preview", "interrupt"]

负向断言才是真正的约束：

  • 澄清时不得出现预览；
  • 拒答时不得出现引用；
  • 恢复时不得重发预览。

五、判定强度按风险分级

风险判定方式例子
资金 / 安全 / 协议硬断言，零容忍金额字符串、无地址、事件配对
业务语义软断言，允许波动该出现的事件、错误码
回答质量不在这里测交给 RAG 专项与 Judge

原因很实际：LLM 输出有随机性，把「回答里有没有某个词」做成硬门禁， 会让流水线长期飘红，最后没人看告警。

六、用 status 表达成熟度，而不是写假用例

  • active：现在就该通过；
  • pending：依赖未实现能力（e2e-09、e2e-16、e2e-20）；
  • active + note：已知实现偏差，用例跟随现状（e2e-03、e2e-11）。

这比「先写一条必然失败的用例占位」更好：基线始终可信，缺口也不会被忘记。

七、数据和真实请求对齐

  • 使用真实措辞，不用 test bridge 100 这类占位文本；
  • 跨链用例带真实格式的收款地址；
  • 中英文各覆盖，因为检索是跨语言的；
  • 金额使用会触发边界的值（0、10.0000001）。

否则用例通过了，也只能证明「测试语料能通过」。

八、明确不测什么

端到端刻意不覆盖：回答是否忠于文档、检索排名质量、并发与压测、真实重启恢复。 这些留给下层评测，避免 e2e 变成又慢又贵的「万能测试」。

总结：从入口和可观察事件倒推，沿决策树枚举分支，用成对用例锁规则， 用双向断言防漏判，用强度分级防误伤，用 status 记录成熟度。

Q05

一次 /chat 请求从进入到返回，代码怎么走？

一句话：uvicorn → Starlette → chat → _stream → ainvoke → 各节点 → _state_events → _encode → socket。 接口函数本身只负责“打包响应”，真正的业务在响应头发出后才开始执行。

一、总链路

① uvicorn（ASGI 服务器）
   └─ await app(scope, receive, send)
      app 由 create_app() 创建                      app.py
      （生产由 build_app() 装配）                    config.py

② Starlette 路由
   └─ chat(payload)                                app.py
      ├─ ChatRequest 校验（Pydantic）                core/models.py
      │    失败 → 422，不进函数
      └─ initial_state(session_id, message)        orchestration/state.py   ← 立即执行
            → _stream(...)                         app.py                   ← 只创建生成器
            → StreamingResponse(...) 返回

③ Starlette 发送响应头，然后 async for 驱动生成器

④ _stream 第一次 __anext__
   └─ graph.ainvoke(run_input, thread_config(session_id))
      thread_config                                orchestration/state.py
      编译图来自 build_graph()                      orchestration/graph.py
      checkpointer 来自 build_checkpointer()        config.py
                      / make_checkpointer()         state.py
      → 按 thread_id 读 Redis，合并历史

⑤ LangGraph 逐节点执行（每个节点被 catching 包裹）   nodes.py
   ├─ entry 节点                                   nodes.py
   ├─ router 节点                                  nodes.py
   │   └─ route(message, llm)                      routing/router.py

四、谁触发 __anext__

驱动代码不在本仓库，在安装的 Starlette 包中：

async def stream_response(self, send: Send) -> None:
    await send({"type": "http.response.start", ...})          # 先发响应头
    async for chunk in self.body_iterator:                    # 驱动器
        if not isinstance(chunk, bytes | memoryview):
            chunk = chunk.encode(self.charset)
        await send({"type": "http.response.body", "body": chunk, "more_body": True})
    await send({"type": "http.response.body", "body": b"", "more_body": False})

async for 在 Python 层会反复调用 __anext__()，捕获 StopAsyncIteration 结束， 所以没有单独一行“调用 __anext__”的代码。 上层的 StreamingResponse.__call__ 在 ASGI 2.4+ 直接 await stream_response； 旧协议下则与“监听断连”并发运行，任一方结束就取消另一方。

五、四个易误解点

误解实际
返回 Response 就代表处理完了返回时图还没开始跑，首次迭代才执行
SSE 就是逐 token 输出当前是图跑完后发 1 个 token 事件，整段文本
出错会返回 500响应头已发出，错误只能变成 error 事件，状态码仍 200
initial_state 是完整状态只是本轮增量，历史由 checkpointer 按 thread_id 合并

六、LLM 只出现在三个位置

  • 路由兜底：规则未命中时 complete_structured；
  • 澄清追问：clarify 节点 complete；
  • RAG 生成：respond 节点 complete。

其余全是确定性代码：规则抽取、检索、守卫、槽位校验、模拟、预览组装。

两个实现细节： 节点统一被 catching 包裹，异常不会让图崩掉，而是写成 state["error"]； interrupt 不是 SSE 原生概念，而是 LangGraph 的暂停机制，网关只是把“存在 __interrupt__”翻译成一条事件。

Q06

评测器是怎么读 SSE 的？flush() 是什么？

_post_stream 只做三件事：流式发请求 → 按帧解析 → 返回事件列表。 它不用第三方 SSE 库，而是手工实现协议，好处是坏帧也能留下证据。

一、三步读取

# 1. 保持连接打开，逐行消费
async with client.stream("POST", url, json=payload) as response:

    # 2. 非 200 先读完错误体，再抛异常
    if response.status_code != 200:
        body = (await response.aread()).decode("utf-8", "replace")
        raise StreamError(f"HTTP {response.status_code}: {body[:300]}")

    # 3. 200 才进入流式解析
    return await _read_stream(response)
调用作用何时使用
client.stream(...)拿到响应头和未读的响应体句柄总是
response.aread()把整个体读进内存仅非 200 分支
response.aiter_lines()逐行拉取，边到边处理200 分支

response 不是字符串内容，而是一个连着网络的句柄： 状态行和响应头已收到，响应体还在传输中。此时访问 .text 会抛 ResponseNotRead。

二、flush()：提交一帧

它不是网络缓冲区的 flush，而是 _read_stream 内部定义的提交函数。 SSE 一帧由多行累积而成，必须等空行才能解码： 

def flush():
    nonlocal name, data_lines
    if name is None:          # 没有事件名，丢弃残留
        data_lines = []
        return
    raw = "\n".join(data_lines)      # 多个 data 行拼接
    events.append(_decode_event(name, raw))
    name = None                      # 重置，准备下一帧
    data_lines = []
  • 遇到空行调用一次：当前帧收齐，解析并入库；
  • 循环结束后再调用一次：最后一帧可能没有结尾空行，否则会丢事件；
  • 必须 nonlocal，否则修改的是局部变量，外层缓冲永远不变。

三、读取何时结束

结束方式条件结果
正常结束服务端关闭连接 / 体读完最后一次 flush()，返回事件列表
读超时超过 timeout 没有新数据ReadTimeout → StreamError
连接异常断连、协议错误HTTPError → StreamError

SSE 没有 done 事件，连接关闭就是结束信号。 所以正常读完和“被中断”在协议层无法区分，这也是后续建议补结束事件的原因。

Q07

没有标准答案，评测结论怎么得出？oracle 是什么？

Oracle（测试预言）是判断“实际结果对不对”的权威依据。 它不等于期望值，而是期望值 + 比较规则的组合。

一、三个词要分清

概念含义本项目对应
期望 expected“应该是多少”amount 应为 100
oracle 判定机制“怎么算对”check_expect 的规则
断言 assertion执行判定的动作failures.append(...)

二、oracle 的强弱

类型判定方式例子
精确值完全相等amount == "100"、error_code == "invalid_amount"
结构形状 / 类型 / 必填引用必须含四个字段
集合必须出现 / 禁止出现events / forbidden
启发式关键词、阈值text_contains_any
人工人来判Judge 校准、抽检
一致性多次运行或多版本对比3 次中位数对比基线

RAG 答案没有唯一文本，逐字比对必然误判，这就是 test oracle problem。 应对方式不是找标准答案，而是换一种 oracle：判行为、判约束、判结构。

三、RAG 与 Bridge 的断言差异

维度RAGBridge
oracle 强度结构 + 存在性字段值精确
随机源LLM 生成仅路由兜底，多数 0 次
核心断言events、forbidden、citations_resolvepreview_fields、error_code
硬断言引用结构、不得编造路径金额精度、拒绝先于预览
主要盲区内容正确性、引用是否支撑上游失败、恢复批准路径
结论回答“协议对不对”“算得对不对”

四、data 的边界

data 的形状在测试意图内，含义不在：

内容是否断言归属
合法 JSON、token.text 非空是，hardL5
引用非空、字段齐全、score 为数字是，hardL5
预览字段齐全、amount 为字符串是，hardL5
回答是否正确、引用是否支撑结论否L3

后果是：一段“引用结构完整但内容胡编”的回答，可以在 e2e 中通过。 这正是 L3 生成专项存在的理由。

五、结论怎么得出

每个 case：failures 为空 → passed，否则 failed（区分 hard / soft）
整体：pass_rate = passed / executed
      hard_failures = 0  → 契约没破
      soft_failures > 0 → 质量或业务期望未达成

所以“16 通过 / 1 失败 / 硬失败 0”的含义是： 17 条可执行用例中 16 条满足全部约束，没有任何一条违反硬契约， 而不是“16 条回答都正确”。

Q09

为什么要设计 SSE 事件？是我们自创的吗？

不是自创。“在流上发带类型的事件”是行业通行做法， 我们只是按业务给事件起了名字。

一、五个事件对应五种客户端动作

事件客户端动作
token渲染文本
citations在文本下方挂引用
tx_preview弹出交易确认框
interrupt停止自动流程，等人确认
error展示错误，按码处理

如果只有一个 data，客户端只能猜“文本里有没有预览信息”，既不可靠也无法自动化。 事件名就是类型判别器。

二、四个设计理由

  • 异构载荷需要判别：文本、引用、预览、错误结构差异极大；
  • 暂停是控制信号：“请确认”写在文本里不等于协议真的暂停；
  • 支持分批到达：SSE 允许先发文本、再发引用；
  • 契约稳定：内部状态怎么改，前端与评测器只依赖事件。

三、业界对照

系统做法
OpenAI Chat CompletionsSSE + data: [DONE]
Anthropic Messagesmessage_start、content_block_delta、message_stop
Vercel AI SDKtext-delta、tool-call、finish
LangGraph 平台updates、messages、custom 多模式
AG-UITEXT_MESSAGE_CONTENT、TOOL_CALL_START、RUN_FINISHED

四、我们与行业的两点差异

差异影响
没有正常结束事件无法区分“正常结束”和“连接被中断”，也无法携带结束原因
事件名按业务命名tx_preview 不可复用；通用做法是 action_proposal + 业务字段

一句话：事件把“服务端内部状态”翻译成“客户端可执行的动作”。 文本解决“说什么”，事件解决“接下来该做什么”。

Q10

大多数 Agent 都有路由层吗？

行为上大多数都有，但不一定是一个独立的路由节点。 分流可能藏在模型里、工具调用里，或框架里。

一、四种常见形态

形态实现场景
显式路由节点独立 classify 步骤，输出 intentLangGraph 多分支、多 Agent
工具选择LLM 输出 function callReAct、编码 Agent
语义路由embedding 相似度匹配处理链客服分流、成本优化
级联路由规则/小模型先判，不确定再上大模型高并发、成本敏感

还有一类隐式路由：单 Agent 循环里模型自己决定“要不要检索、要不要调工具”。 没有 Router 模块，但分流行为客观存在。

二、为什么需要路由

动机说明
成本简单问题不必走大模型或长链路
延迟规则命中可毫秒级返回
确定性关键分支不交给模型自由发挥
安全高风险操作必须先过校验
可观测路由结果可记录、可评测、可归因

本项目是「规则优先 + LLM 兜底」，属于级联路由的变体。

三、显式 vs 隐式

显式路由隐式路由
可控性高，可写规则低，随模型漂移
成本多数不调 LLM每次都要推理
评测可单独测准确率难以归因
维护需持续补规则靠提示词与模型能力
风险规则覆盖不全时误判不稳定、难审计

四、什么时候不需要

  • 产品只有一个功能，例如纯文档问答；
  • 只有一个工具，调不调结果都一样；
  • 流程完全固定，没有分支。

判断一个 Agent 有没有路由，看五个信号：是否存在 intent/route 字段、提示词是否让模型选分支、 是否按场景切换系统提示词、是否有“先查库还是先查工具”的逻辑、工具列表是否随场景变化。 命中任意一条，就存在事实上的路由层。
